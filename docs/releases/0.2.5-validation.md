## Report storage coverage

- Create and update accept the 10,485,760-character Markdown boundary and
  reject larger Markdown with `400`.
- The report route accepts a request at the configured 50 MiB boundary and
  returns `413` above it for an authenticated incident member. Unauthenticated
  requests are rejected before parsing the larger body. Other JSON endpoints
  keep the default 100 KiB limit.
- Large generated context and Markdown survive create, list, read, update, and
  export while PostgreSQL stores only metadata and the content-file reference.
- Existing inline reports remain readable and move to file storage when their
  Markdown is edited.
- Missing, corrupt, traversal-like, or unwritable report files fail safely
  without exposing file paths or content.
- Insert, update, request, and commit failures preserve the previous report and
  clean up uncommitted files. Successful replacement and deletion remove old
  files after commit.
- Legacy databases with an empty migration history baseline migrations through
  `010` and still apply `011`; repeated migration runs preserve existing report
  content.

## Release workflow coverage

- Pull requests and version tags run CI; pushes to `main` do not repeat the
  validation job.
- A `main` release run publishes only when exactly one new semver tag becomes
  reachable and its tag CI run succeeded.
- The resolver checks that the tag matches `package.json`, then builds the exact
  tagged commit. Ordinary `main` pushes skip publication.
- Manual publication accepts only a validated release tag already contained in
  `main`.

No customer or production data is required for these checks.
